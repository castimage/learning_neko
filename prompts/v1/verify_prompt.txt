## RULES
- 只有能明确指出问题位置与理由时才判不通过；凭印象觉得「不够好」「可以更详细」不构成不通过理由。
- 逐条核对 criteria 中的每个审核点，任何一条不满足都必须记入 errors。
- 产物与 basis 矛盾、产物引入了 basis 之外的超纲内容、结构化字段取值落在枚举之外、内部引用指向不存在的标识，这四类问题一律判不通过。
- 产物对 basis 的概括、缩写、换用同义表达，只要语义一致就不算问题；只有语义矛盾、方向相反或事实错误才判不通过。
- 节点或字段的文本不必逐字对齐 basis，判断依据是它表达的意思是否与 basis 一致，而不是字符是否相同。
- 产物在 basis 基础上给出的合理例子、算例或说明，只要不引入 basis 未涵盖的新概念体系，就不算超纲。
- 分组如何划分、布局方向选哪种、节点数量多少、命名风格与措辞偏好，都属于组织偏好而非缺陷，不构成不通过理由。
- 每条 error 的 content 必须引用产物中的具体片段或具体字段名；reason 必须说明它违反了哪一条审核点；fix 必须写成可直接执行的修改动作。
- 产物全部通过时，errors 返回空数组，pass 置为 true。
- 不要因为产物风格、篇幅或措辞偏好而判不通过。
- 结构化字段的取值是否合法由解码层强制，非法取值根本不会送到你这里。因此不要去核查某个取值是否在你的枚举里，也不要因为「这个取值我没在 criteria 的文字里见过」就判不通过，你只负责判断语义是否成立。

## INPUT
审核点见 criteria，原始材料见 basis，待审产物见 artifact。

## TASK
核查该产物是否满足全部审核点，输出核查结论与问题清单。

## OUTPUT
输出为 JSON 对象，字段含义与取值要求如下：
- pass：布尔值，全部审核点通过时为 true，存在任一问题时为 false。
- errors：对象数组，每个元素含：
  - content：字符串，产物中出问题的具体片段或字段名。
  - reason：字符串，它违反了哪一条审核点、为何构成问题。
  - fix：字符串，可直接执行的修正动作，需指明改成什么。

## EXAMPLES
若产物是一道单选题，其 answer 写的是「以上都对」，而选项里并不存在该项：
- pass：false
- errors：[{"content": "exercises[0].answer = \"以上都对\"", "reason": "违反了「answer 必须唯一确定且不得出现『以上都对』这类选项」的审核点，且该值不在 options 列表内，答案与选项不自洽。", "fix": "把 answer 改为 options 中语义正确的那个选项原文，或在 options 中补入该项并确认其唯一正确性。"}]

## SELF-CHECK
交付前逐条自检，任一项不满足则先修正再输出：
- pass 与 errors 是否一致？即 pass 为 true 时 errors 必须为空数组。
- 每条 error 的 content 是否指向了产物中真实存在的片段或字段？
- 每条 fix 是否写成了可执行的修改动作，而非「需要改进」这类描述？
- 是否存在仅凭风格偏好而记录的问题？若有则删除。
